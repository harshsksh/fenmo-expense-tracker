## OVERVIEW

Assignment:  Build a personal finance expense tracker with a REST API and React frontend.
Tech Stack:  Next.js 14 (App Router), Neon (PostgreSQL) via Prisma ORM, Tailwind CSS
Deployment:  Vercel (frontend + API routes) + Neon (serverless PostgreSQL — free tier)

Why Next.js:
- Single repo, single deployment — API routes + frontend in one project
- No CORS setup needed — API and UI share the same origin
- Built-in file-based routing for both pages and API endpoints
- Easy deployment to Vercel with zero config

Why Neon (over SQLite):
- Fully managed, serverless PostgreSQL — no Docker, no local DB daemon needed
- Persistent across every Vercel deployment (SQLite on Vercel resets on each deploy)
- Free tier covers this project with no credit card required
- Scales to production — same DB you'd use in a real app
- Works perfectly with Vercel's serverless functions via connection pooling

Why Prisma:
- Single schema file — swap providers by changing one line if needed
- Fully type-safe queries — no `as any` casting on raw DB rows
- Built-in migration system — replaces manual migration functions
- Native PostgreSQL enum support for category validation at DB level

### 0.4 — Environment Variables

Neon provides two connection strings in the dashboard:

1. Direct connection (for migrations and local dev)
2. Pooled connection (for serverless / production — use with `?pgbouncer=true`)

Update `.env` (generated by `prisma init`):

```
# .env
# Direct connection — used for `prisma migrate dev` and local development
DATABASE_URL="postgresql://user:password@ep-xxx.region.aws.neon.tech/neondb?sslmode=require"

# Pooled connection — used by the app in production (Vercel serverless)
# Get this from Neon dashboard → Connection Details → Pooled connection
DATABASE_URL_UNPOOLED="postgresql://user:password@ep-xxx-pooler.region.aws.neon.tech/neondb?pgbouncer=true&sslmode=require"
```

Create `.env.example` (commit this, NOT `.env`):
```
DATABASE_URL="postgresql://user:password@ep-xxx.region.aws.neon.tech/neondb?sslmode=require"
DATABASE_URL_UNPOOLED="postgresql://..."
```

> **Why two URLs?** Neon's connection pooler (PgBouncer) is essential in serverless
> environments where each function invocation opens a new DB connection. Without pooling,
> you quickly hit Neon's 1,000-connection limit. The pooler reuses connections efficiently.
> Prisma migrations must use the direct (non-pooled) URL.

### 0.6 — Data Model Decision (CRITICAL — Read Before Coding)

NEVER store money as FLOAT. Floating point arithmetic causes bugs:
  0.1 + 0.2 = 0.30000000000000004

CORRECT approach:
  - Store amount as INTEGER in paise (₹149.99 → stored as 14999)
  - Convert rupees → paise on write:  Math.round(amount * 100)
  - Convert paise → rupees on read:   amount / 100
  - Sum totals using paise integers, divide by 100 ONCE at the end for display

### 1.1 — Prisma Schema (prisma/schema.prisma)

With Neon (PostgreSQL), you get native enum support at the DB level —
Prisma enforces valid categories in the schema itself, not just in application code.

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider  = "postgresql"
  url       = env("DATABASE_URL")       // Direct connection (used for migrations)
  directUrl = env("DATABASE_URL_UNPOOLED") // Pooled connection (used by app at runtime)
}

// PostgreSQL native enum — Neon enforces this at the DB level
enum Category {
  Food
  Transport
  Shopping
  Bills
  Health
  Entertainment
  Other
}

model Expense {
  id          String   @id                 // UUID v4 — client-generated for idempotency
  amount      Int                          // Stored in PAISE (₹1 = 100). NEVER Float.
  category    Category                     // DB-level enum — invalid values are rejected
  description String
  date        String                       // YYYY-MM-DD string
  created_at  DateTime @default(now())

  @@index([category])
  @@index([date])
}
```

> **url vs directUrl:** Prisma uses `url` for runtime queries (goes through PgBouncer pooler)
> and `directUrl` for migrations (bypasses pooler, requires a direct connection).
> This split is required for Neon + Prisma to work correctly on Vercel.

Run the initial migration after setting up your `.env`:
```bash
npx prisma migrate dev --name init
```

This creates:
- `prisma/migrations/` folder with versioned SQL files (commit these)
- The `Category` enum and `Expense` table in your Neon database
- Generates the Prisma Client with full TypeScript types

Every time you change `schema.prisma`, run:
```bash
npx prisma migrate dev --name describe_your_change
```

### 1.2 — Prisma Client Singleton (lib/prisma.ts)

Next.js hot-reloading creates new module instances in development.
Without this singleton, you get "too many connections" warnings.

```typescript
import { PrismaClient } from '@prisma/client';

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined;
};

export const prisma =
  globalForPrisma.prisma ??
  new PrismaClient({
    log: process.env.NODE_ENV === 'development' ? ['query', 'error', 'warn'] : ['error'],
  });

if (process.env.NODE_ENV !== 'production') {
  globalForPrisma.prisma = prisma;
}

export default prisma;
```

> **Why globalThis:** In development, Next.js reloads modules on each save.
> Without caching on `globalThis`, a new `PrismaClient` is created on every hot
> reload, quickly exhausting Neon's connection limit. In production on Vercel,
> each serverless function invocation is isolated, so the singleton applies only
> within a single invocation — the pooler handles the rest.

### 1.3 — Money Helper (lib/money.ts)

```typescript
// Rupees (float) → Paise (integer) — use when SAVING to DB
export function rupeesToPaise(rupees: number): number {
  return Math.round(rupees * 100);
}

// Paise (integer) → Rupees (float) — use when READING from DB
export function paiseToRupees(paise: number): number {
  return paise / 100;
}

// Format rupees for display: 1234.5 → "₹1,234.50"
export function formatRupees(rupees: number): string {
  return new Intl.NumberFormat('en-IN', {
    style: 'currency',
    currency: 'INR',
    minimumFractionDigits: 2,
  }).format(rupees);
}
```

### 1.4 — Validation Helper (lib/validate.ts)

With Neon's native PostgreSQL enum, the DB itself rejects invalid categories.
The application-level validation below is a fast-fail layer before hitting the DB.

```typescript
import { CATEGORIES } from '@/types/expense';

export interface ValidationError {
  field: string;
  message: string;
}

export function validateExpenseInput(body: unknown): ValidationError[] {
  const errors: ValidationError[] = [];
  if (!body || typeof body !== 'object') return [{ field: 'body', message: 'Invalid request body' }];

  const b = body as Record<string, unknown>;

  // id
  if (!b.id || typeof b.id !== 'string' || b.id.trim() === '')
    errors.push({ field: 'id', message: 'id is required' });

  // amount
  const amount = parseFloat(String(b.amount));
  if (isNaN(amount) || amount <= 0)
    errors.push({ field: 'amount', message: 'Amount must be a positive number' });
  if (amount > 999999)
    errors.push({ field: 'amount', message: 'Amount cannot exceed ₹9,99,999' });

  // category — validated here AND enforced by PostgreSQL enum in Neon
  if (!CATEGORIES.includes(b.category as any))
    errors.push({ field: 'category', message: 'Invalid category' });

  // description
  if (!b.description || typeof b.description !== 'string' || b.description.trim() === '')
    errors.push({ field: 'description', message: 'Description is required' });
  if (typeof b.description === 'string' && b.description.length > 200)
    errors.push({ field: 'description', message: 'Description max 200 characters' });

  // date
  const dateRegex = /^\d{4}-\d{2}-\d{2}$/;
  if (!b.date || !dateRegex.test(String(b.date)) || isNaN(Date.parse(String(b.date))))
    errors.push({ field: 'date', message: 'Date must be a valid YYYY-MM-DD string' });

  return errors;
}
```

### 2.1 — Route File (app/api/expenses/route.ts)

Next.js App Router uses named exports GET, POST in route.ts files.
Prisma + Neon replaces all raw SQL with type-safe method calls.

```typescript
import { NextRequest, NextResponse } from 'next/server';
import prisma from '@/lib/prisma';
import { validateExpenseInput } from '@/lib/validate';
import { rupeesToPaise, paiseToRupees } from '@/lib/money';
import { Category } from '@prisma/client'; // generated from your Prisma enum

// Helper: convert a Prisma Expense row → client-safe shape (paise → rupees)
function serializeExpense(expense: {
  id: string;
  amount: number;
  category: Category;
  description: string;
  date: string;
  created_at: Date;
}) {
  return {
    ...expense,
    amount: paiseToRupees(expense.amount),
    created_at: expense.created_at.getTime(), // Date → Unix ms for JSON
  };
}

// ─── GET /api/expenses ────────────────────────────────────────────────────────
export async function GET(request: NextRequest) {
  try {
    const { searchParams } = new URL(request.url);
    const categoryParam = searchParams.get('category');

    // Validate category param against Prisma-generated enum values
    const category =
      categoryParam && Object.values(Category).includes(categoryParam as Category)
        ? (categoryParam as Category)
        : undefined;

    const expenses = await prisma.expense.findMany({
      where: category ? { category } : undefined,
      orderBy: [
        { date: 'desc' },
        { created_at: 'desc' },
      ],
    });

    return NextResponse.json(expenses.map(serializeExpense));
  } catch (error) {
    console.error('[GET /api/expenses]', error);
    return NextResponse.json({ error: 'Internal server error' }, { status: 500 });
  }
}

// ─── POST /api/expenses ───────────────────────────────────────────────────────
export async function POST(request: NextRequest) {
  try {
    const body = await request.json();

    // Validate
    const errors = validateExpenseInput(body);
    if (errors.length > 0) {
      return NextResponse.json({ errors }, { status: 400 });
    }

    const { id, amount, category, description, date } = body;
    const amountPaise = rupeesToPaise(parseFloat(String(amount)));

    // upsert with empty update = idempotent insert
    // If the ID already exists, return the existing record unchanged.
    const expense = await prisma.expense.upsert({
      where: { id: id.trim() },
      create: {
        id: id.trim(),
        amount: amountPaise,
        category: category as Category, // safe — validated above
        description: description.trim(),
        date,
      },
      update: {}, // empty update = don't overwrite on duplicate
    });

    const isNew = expense.created_at.getTime() > Date.now() - 2000;

    return NextResponse.json(
      serializeExpense(expense),
      { status: isNew ? 201 : 200 }
    );
  } catch (error) {
    console.error('[POST /api/expenses]', error);
    return NextResponse.json({ error: 'Internal server error' }, { status: 500 });
  }
}
```

> **Category import from `@prisma/client`:** Because you defined `Category` as a
> Prisma enum, Prisma generates it as a TypeScript enum in the client. Import it
> directly instead of from `types/expense.ts` in the route — this keeps the DB
> type and the app type in sync automatically.

### 2.2 — Idempotency — The Most Critical Feature

PROBLEM: User submits form → network times out → user sees error and submits again.
Without idempotency: two identical expense rows in the database.
With idempotency: same expense stored exactly once.

HOW IT WORKS:
1. Client generates a UUID when the form is first rendered (NOT on each click).
2. UUID is included in every POST body as the "id" field.
3. Backend uses `prisma.expense.upsert` with `update:{}` — if ID already exists,
   the update block is empty so nothing changes.
4. Backend always fetches and returns the existing record.
5. Client reuses same UUID on retry (same form state = same UUID).
6. Client generates a NEW UUID only after a successful submission + form reset.

This correctly handles:
- Double-click on submit button
- Network timeout + retry
- Page refresh mid-submission
- Browser back + resubmit

```typescript
import { CreateExpenseInput, Expense } from '@/types/expense';

const BASE = '/api'; // same-origin — no CORS needed with Next.js

export async function fetchExpenses(category?: string): Promise<Expense[]> {
  const url = category ? `${BASE}/expenses?category=${category}` : `${BASE}/expenses`;
  const res = await fetch(url);
  if (!res.ok) {
    const err = await res.json().catch(() => ({}));
    throw new Error(err.error || 'Failed to fetch expenses');
  }
  return res.json();
}

export async function createExpense(input: CreateExpenseInput): Promise<Expense> {
  const res = await fetch(`${BASE}/expenses`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(input),
  });
  if (!res.ok) {
    const err = await res.json().catch(() => ({}));
    throw new Error(err.errors?.[0]?.message || err.error || 'Failed to create expense');
  }
  return res.json();
}
```

### 3.2 — Custom Hook (hooks/useExpenses.ts)

```typescript
'use client';
import { useState, useEffect, useCallback } from 'react';
import { Expense } from '@/types/expense';
import { fetchExpenses, createExpense } from '@/lib/api-client';
import { CreateExpenseInput } from '@/types/expense';

export function useExpenses(category?: string) {
  const [expenses, setExpenses] = useState<Expense[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  const loadExpenses = useCallback(async () => {
    setLoading(true);
    setError(null);
    try {
      const data = await fetchExpenses(category || undefined);
      setExpenses(data);
    } catch (err: any) {
      setError(err.message);
    } finally {
      setLoading(false);
    }
  }, [category]);

  useEffect(() => {
    loadExpenses();
  }, [loadExpenses]);

  const addExpense = async (input: CreateExpenseInput): Promise<Expense> => {
    // Optimistic update: add to list immediately
    const optimistic: Expense = { ...input, amountPaise: 0, created_at: Date.now() };
    setExpenses(prev => [optimistic, ...prev]);
    try {
      const created = await createExpense(input);
      // Replace optimistic entry with real server response
      setExpenses(prev => prev.map(e => e.id === input.id ? created : e));
      return created;
    } catch (err) {
      // Rollback on failure
      setExpenses(prev => prev.filter(e => e.id !== input.id));
      throw err;
    }
  };

  // Compute total from current list (use integer paise for precision, divide once)
  const total = expenses.reduce((sum, e) => sum + Math.round(e.amount * 100), 0) / 100;

  return { expenses, loading, error, total, addExpense, refresh: loadExpenses };
}
```

### 3.4 — ExpenseForm Component (components/ExpenseForm.tsx)

KEY POINTS:
- UUID is generated on component mount using `crypto.randomUUID()`
- Same UUID persists across submit retries (same form state)
- New UUID generated only after SUCCESSFUL submission + form reset
- Submit button disabled while request is in-flight

```typescript
'use client';
import { useState } from 'react';
import { CATEGORIES, CreateExpenseInput } from '@/types/expense';

interface Props {
  onAdd: (input: CreateExpenseInput) => Promise<any>;
}

const today = () => new Date().toISOString().split('T')[0];
const newId = () => crypto.randomUUID();

export default function ExpenseForm({ onAdd }: Props) {
  const [idempotencyKey, setIdempotencyKey] = useState(newId);
  const [amount, setAmount]           = useState('');
  const [category, setCategory]       = useState(CATEGORIES[0]);
  const [description, setDescription] = useState('');
  const [date, setDate]               = useState(today());
  const [submitting, setSubmitting]   = useState(false);
  const [fieldErrors, setFieldErrors] = useState<Record<string, string>>({});
  const [submitError, setSubmitError] = useState('');

  function validateForm(): boolean {
    const errors: Record<string, string> = {};
    if (!amount || isNaN(parseFloat(amount)) || parseFloat(amount) <= 0)
      errors.amount = 'Enter a valid positive amount';
    if (parseFloat(amount) > 999999)
      errors.amount = 'Amount cannot exceed ₹9,99,999';
    if (!description.trim())
      errors.description = 'Description is required';
    if (description.length > 200)
      errors.description = 'Max 200 characters';
    if (!date)
      errors.date = 'Date is required';
    setFieldErrors(errors);
    return Object.keys(errors).length === 0;
  }

  async function handleSubmit(e: React.FormEvent) {
    e.preventDefault();
    if (!validateForm()) return;

    setSubmitting(true);
    setSubmitError('');

    try {
      await onAdd({
        id: idempotencyKey,
        amount: parseFloat(amount),
        category,
        description: description.trim(),
        date,
      });
      // SUCCESS: reset form and generate new idempotency key
      setAmount('');
      setDescription('');
      setDate(today());
      setCategory(CATEGORIES[0]);
      setIdempotencyKey(newId());
    } catch (err: any) {
      setSubmitError(err.message || 'Submission failed. Please try again.');
      // NOTE: idempotencyKey is NOT regenerated on error — retrying is idempotent.
    } finally {
      setSubmitting(false);
    }
  }

  return (
    <form onSubmit={handleSubmit} className="bg-white border border-gray-200 rounded-xl p-5">
      <h2 className="text-base font-medium mb-4">Add Expense</h2>
      <div className="grid grid-cols-2 gap-3">

        {/* Amount */}
        <div>
          <label className="block text-sm text-gray-600 mb-1">Amount (₹)</label>
          <input
            type="number" step="0.01" min="0.01" max="999999"
            value={amount} onChange={e => setAmount(e.target.value)}
            placeholder="0.00"
            className="w-full border border-gray-300 rounded-lg px-3 py-2 text-sm"
          />
          {fieldErrors.amount && <p className="text-red-500 text-xs mt-1">{fieldErrors.amount}</p>}
        </div>

        {/* Category */}
        <div>
          <label className="block text-sm text-gray-600 mb-1">Category</label>
          <select
            value={category} onChange={e => setCategory(e.target.value)}
            className="w-full border border-gray-300 rounded-lg px-3 py-2 text-sm"
          >
            {CATEGORIES.map(c => <option key={c}>{c}</option>)}
          </select>
        </div>

        {/* Description */}
        <div className="col-span-2">
          <label className="block text-sm text-gray-600 mb-1">
            Description
            <span className="ml-1 text-gray-400">({description.length}/200)</span>
          </label>
          <input
            type="text" maxLength={200}
            value={description} onChange={e => setDescription(e.target.value)}
            placeholder="e.g. Lunch at Cafe Coffee Day"
            className="w-full border border-gray-300 rounded-lg px-3 py-2 text-sm"
          />
          {fieldErrors.description && <p className="text-red-500 text-xs mt-1">{fieldErrors.description}</p>}
        </div>

        {/* Date */}
        <div>
          <label className="block text-sm text-gray-600 mb-1">Date</label>
```

### 4.2 — Money Precision Testing

Test these amounts end-to-end (submit → fetch → display):
- ₹0.01   → stored as 1 paise   → displayed as ₹0.01
- ₹0.99   → stored as 99 paise  → displayed as ₹0.99
- ₹1.50   → stored as 150 paise → displayed as ₹1.50
- ₹1234.56 → stored as 123456  → displayed as ₹1,234.56
- ₹99999.99 → stored as 9999999 → displayed as ₹99,999.99

Total calculation — sum using integers:
```typescript
// WRONG — float accumulation error
const total = expenses.reduce((sum, e) => sum + e.amount, 0);

// CORRECT — integer paise sum, divide once
const total = expenses.reduce((sum, e) => sum + Math.round(e.amount * 100), 0) / 100;
```

### 4.3 — Category Validation (Two Layers)

With Neon, you have validation at TWO layers — both should pass:

Layer 1 — Application (`validate.ts`):
Fast-fail before a DB round-trip. Returns a 400 with a user-friendly message.

```typescript
if (!CATEGORIES.includes(body.category as any)) {
  return 400 with error message
}
```

Layer 2 — PostgreSQL enum in Neon:
If somehow an invalid value reaches the DB, PostgreSQL rejects it with a
constraint error. This is a safety net — the app layer should always catch it first.

> **Unlike SQLite:** SQLite stores enums as plain text and has no type enforcement.
> PostgreSQL's native enum is a real DB constraint — Neon will reject `category = 'InvalidValue'`
> at the query level even if application validation is bypassed.

---

### 4.4 — SQL Injection Prevention

Prisma uses parameterized queries internally for ALL operations. Unlike raw SQL,
there is no way to accidentally interpolate user input into a query string.
No additional precautions needed beyond using Prisma methods.

```typescript
// Prisma handles parameterization automatically — this is safe:
await prisma.expense.findMany({ where: { category } });

// Avoid this unless absolutely necessary:
await prisma.$queryRaw`SELECT * FROM expenses WHERE category = ${category}`;
// ^ If you must use $queryRaw, the tagged template literal DOES parameterize correctly.
```

### 4.5 — Network & Error Scenarios

Scenario 1 — API is down when page loads:
  Expected: Show error message with Retry button. Never blank page.

Scenario 2 — Form submit fails mid-flight:
  Expected: Optimistic row disappears (rollback). Error message shown inline.
  Form data is preserved so user can retry without re-typing.

Scenario 3 — Invalid data from client:
  Expected: 400 response with specific field error. Frontend shows it near the field.

Scenario 4 — Category filter with no matching results:
  Expected: Empty state message ("No expenses in this category"), not an error.

Scenario 5 — Neon cold start latency:
  Neon pauses compute after 5 minutes of inactivity on the free tier. The first
  request after a pause takes ~500ms–1s to wake up. Show the loading skeleton so
  the user sees activity rather than a blank screen.

---

### 4.6 — Input Edge Cases

- Amount field: block non-numeric characters via `type="number"`
- Amount: reject 0 and negative numbers client-side AND server-side
- Description: trim whitespace before save (prevent entries with only spaces)
- Date: `max={today()}` on input to prevent future dates
- Description length: enforce 200-char max with counter display
- Category: use a predefined select, never a free-text field

## Design Decisions

### Why Next.js
Single repo, single deployment, no CORS configuration. API routes and UI share
the same origin. Evaluators can run the full stack with one command.

### Why Neon (PostgreSQL) + Prisma
Neon is a serverless PostgreSQL database that persists across Vercel deployments —
unlike SQLite, which resets on each deploy. Prisma provides type-safe queries and
a built-in migration system. The database schema is the single source of truth:
changing the provider (e.g. to another PostgreSQL host) requires changing one
line in `schema.prisma`. No query rewrites at all.

### Why Neon over a Local PostgreSQL or SQLite
SQLite on Vercel is ephemeral — data resets on every deploy. A local PostgreSQL
requires Docker or a daemon. Neon requires no infrastructure: sign up, paste the
connection string, and you have a persistent PostgreSQL instance in seconds.
The free tier is sufficient for personal use indefinitely.

### Money as Integer (Paise)
Floating point cannot reliably represent decimal currency values. All amounts are
stored as integers in paise (₹1 = 100 paise) and converted only at display time.
This avoids ₹0.1 + ₹0.2 = ₹0.30000000000000004 errors in totals.

### Idempotency via Client-Generated UUID + Prisma Upsert
The client generates a UUID when the form renders. On retry after a network
failure, the same UUID is sent. The backend uses `prisma.expense.upsert` with an
empty update block — if the ID already exists, nothing is overwritten and the
existing record is returned. This prevents duplicate entries from double-clicks
or network retries.

### Optimistic UI Updates
When a new expense is submitted, it is added to the list immediately without
waiting for the API response. If the request fails, the entry is rolled back.
This makes the UI feel fast even on slow connections.

### Two-Layer Category Validation
Categories are validated in application code (fast-fail, user-friendly error)
AND enforced by a PostgreSQL native enum in Neon (DB-level constraint). This
provides defence in depth — even if application validation is bypassed, the
database will reject invalid values.

## Trade-offs Made Due to Time

- No authentication or user sessions
- No edit or delete functionality
- No pagination (acceptable for personal use at small scale)
- Neon free tier pauses compute after 5 minutes idle — first request after
  pause is ~500ms–1s slower (handled gracefully by loading skeleton)

## What I Intentionally Did NOT Do

- No Redux or Zustand — React useState is sufficient for this scope
- No UI component library — plain Tailwind keeps the bundle small
- No debouncing on filter — category changes are instant, no debounce needed
- No date range filter — out of scope per assignment requirements

## If I Had More Time

- Add DELETE and EDIT endpoints
- Add pagination or infinite scroll for large lists
- Add per-category summary chart
- Add more comprehensive test coverage (integration tests per route)
- Add Neon branching for staging environment (create a branch per PR)

1. Using Float for money in Prisma schema
   FIX: Use `Int` in schema.prisma, store paise, convert on read/write

2. Re-generating UUID on each submit click
   FIX: Generate UUID on form mount, only regenerate after successful submit

3. Returning 409 Conflict for duplicate submissions
   FIX: Use `upsert` with `update:{}` — return 200 with existing record

   FIX: Only clear form on success, preserve data on error so user can retry

   FIX: API returns `[]` not null when no results

9. Running `prisma migrate dev` in Vercel build command
   FIX: Run migrations from your local machine. `prisma migrate dev` is

13. Assuming Neon data is always instant after a cold start
    FIX: Neon pauses on the free tier after 5 min idle. Show loading skeletons.

14. Trusting client-sent category values without validation
